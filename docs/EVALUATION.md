# Оценка baseline: cash_left_after_operation

Эта страница описывает исходную разметку v1. После уточнения командой X-15
исключён из данной категории в v2. Актуальное исправление и результаты импорта:
[MANUAL_LABEL_REVIEW.md](MANUAL_LABEL_REVIEW.md). Старые данные не перезаписаны.

Это эксперимент с предобученной локальной Qwen3-VL-2B, не обучение с нуля.
Он проверяет только одну категорию, а не все нарушения кейса.

## Разметка и разделение

- Подтверждённые командой положительные примеры: X-4, X-15, X-26, X-44.
- Отрицательные: исходные видео организаторов «без нарушения», кроме спорного X-12.
- Остальные положительные видео исключены: отсутствие этой категории в них не размечено.
- Байт-в-байт дубликаты объединены по SHA256, используется один представитель.
- Сохранено ранее зафиксированное train/validation-разделение по исходным видео.
- Всего 22 уникальных видео: 4 положительных, 18 отрицательных.
- Train: 16 видео (2 положительных); validation: 6 видео (2 положительных).
  Это очень маленькая предварительная проверка, а не независимый большой тест.
- Обе спорные отметки дубликатов X-4/X-47 требуют дальнейшей проверки для
  точной событийной локализации; в этой версии используется подтверждённый X-4, 57 с.

## Отсутствие утечки разметки

Текущий генератор создаёт исправленную truth v2: X-15 исключён,
21 уникальное видео, train 15 (одно положительное), validation 6 (два положительных).
Подготовка выполняется отдельно; историческую v1 не перезаписывать:

```bash
.venv-ml/bin/python -m ml.datasets.category_manifest --manifest data/processed/review-v1/manifest.csv --output data/processed/cash-category-v2.csv
```

Скрипт инференса выбирает split и передаёт детектору только путь к видео.
В prompt нет ID проверяемого видео, его бинарной метки, размеченного времени
и описаний команды. В варианте с демонстрациями передаются кадры и метки
только отдельных train-видео. Скрипт запрещает использовать validation или
дубликат проверяемого видео как демонстрацию. Это few-shot prompting,
веса модели при этом не обучаются.
Кадры выбираются равномерно через 2 секунды, окна по 6 кадров с перекрытием.
Правильные ответы читает только отдельный scorer после завершения предсказаний.

## Первый результат

Сохранённый прогон `cash-validation-v1`: 6 видео, TP=2, FP=3, TN=0,
один технический сбой чтения видео. Общая accuracy — 33,3%, precision — 40%,
recall — 100%, F1 — 57,1%. Модель «всегда нет нарушения» дала бы 66,7%.
Это слабый результат: найденные нарушения не компенсируют ложные тревоги.
Ошибка чтения исправлена последовательным декодированием кадров.
Последующие проверки после этого результата считаются экспериментами разработки,
а не новым независимым тестом.

Few-shot пилот `cash-fewshot-pilot-v1` использовал train-демонстрации X-15/X-27
и проверял другие train-видео X-5/X-26. Оба завершились сбоем: timeout
254,740 с и невалидный ответ 27,068 с соответственно. Coverage — 0%.
Этот вариант не принят. Лимит времени проверяется между окнами и потому может
быть превышен на время одной генерации; для сервиса нужен жёсткий лимит
отдельного процесса. Данный экспериментальный CLI не заменяет такой watchdog.

Повторный прогон `cash-validation-v2` после исправления декодирования:
все 6 видео обработаны, TP=2, FP=4, TN=0, FN=0. Accuracy — 33,3%,
precision — 33,3%, recall — 100%, F1 — 50%, coverage — 100%.
Модель выдала положительный ответ на каждом видео; результат равен
тривиальной стратегии «всегда нарушение». Детектор не принят для рабочего API.
Максимальное время обработки — 130,705 с, пиковая память MLX — 2,707 ГБ
(не общий расход памяти системы). Время не включает запуск Python и загрузку модели.
Ошибка времени 0,5 с на двух найденных положительных видео не компенсирует
ложные события и не доказывает корректность событийной локализации.

## Следующее улучшение

Сначала нужны проверенные признаки объектов и завершения операции:
отдельно локализовать деньги и место хранения, затем проверять их состояние
до/после завершения обслуживания. Сравнивать следующую версию на том же
development-наборе, сохраняя ложные срабатывания. До итогового заявления о
качестве собрать отдельную тестовую группу с другим ракурсом/съёмкой.
Добавление произвольных сторонних видео само по себе эту ошибку не исправит:
нужны размеченные примеры именно нужных объектов и временных переходов.
Экспериментальный `ml/local_cash.py` пока не подключён к worker.

## Пилот и валидация

Исторический пилот v1 для отладки формата использовал train X-15 и X-27.
В текущей cash-категории X-15 исключён; команды ниже только для сохранённого
архива v1 со снимком исходников того прогона, не для новой генерации v1.
После изменения формата повторять пилот можно; эти результаты не называются
валидационными. На первом пилоте исправлена путаница секунд и индекса кадра.
Конфигурация/хеш prompt и кода сохраняются в run.json каждого прогона.

```bash
.venv-ml/bin/python -m ml.evaluation.run_baseline --manifest data/processed/cash-category-v1.csv --model artifacts/models/qwen3-vl-2b-4bit --output artifacts/evaluations/cash-validation-v1 --split validation
.venv-ml/bin/python -m ml.evaluation.score --manifest data/processed/cash-category-v1.csv --predictions artifacts/evaluations/cash-validation-v1/predictions.jsonl --split validation --output artifacts/evaluations/cash-validation-v1/score
```

Пути выходных каталогов должны быть новыми: прошлые прогоны не перезаписываются.
Для Metal нужен запуск в обычном локальном терминале с доступом к GPU.
Сетевой доступ к Hugging Face при инференсе отключён.

## Что означают метрики

- accuracy_all_videos: правильные ответы / все ожидаемые видео. Сбои, пропуски
  файлов и неопределённые ответы остаются в знаменателе.
- coverage: доля видео, где получено бинарное предсказание.
- accuracy_resolved_only: вспомогательная точность только разрешённых случаев;
  при низком coverage её нельзя выдавать за общее качество.
- precision: TP / (TP + FP); null, если положительных предсказаний нет.
- recall_conservative: TP / все размеченные положительные видео.
- F1: сочетание precision и conservative recall; null при неопределённом precision.
- specificity_conservative: доля правильно отклонённых отрицательных видео;
  сбои/неопределённые ответы считаются ошибками.
- balanced_accuracy_conservative: среднее recall и specificity, если оба класса
  присутствуют. Не позволяет скрыть пропуски нарушений за большим числом отрицательных видео.
- always_negative_accuracy: ориентир для тривиальной модели «нарушения нет».
- time_error: ближайшее предсказанное время к единственному размеченному событию,
  только для совпавших положительных видео. Это оптимистичная вспомогательная
  метрика: не оценивает лишние события и не заменяет событийный precision/recall.
- Время — обработка видео после загрузки модели, включая чтение кадров;
  холодная загрузка, очередь и передача файла учитываются отдельно при проверке API.

Предсказания и сырые ответы сохраняются только локально в artifacts/.
Ошибки JSON не превращаются в «нарушений нет». Неполный ответ помечается failed,
неопределённый — prediction=null; оба явно учитываются в отчёте.

После подбора prompt по validation эта выборка становится частью разработки.
Для финального честного теста потребуются новые съёмки с другим ракурсом или
заранее отложенная группа, не использовавшаяся для изменения подхода.
