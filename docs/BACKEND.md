# Backend Forte DVG

Реализован контракт кейса, загрузка, SQLite-очередь и отдельный worker.
ML-модель НЕ реализована: без ANALYZER_PATH задание завершится
`failed / model_not_configured`, а не выдуманным вердиктом.
Интерфейс пока только проверяет /health; отправку видео в API подключаем отдельно.

## Запуск из корня проекта

1. Остановите старый backend (Ctrl+C).
2. Установите зависимости: `python -m pip install -r requirements.txt`.
3. Скопируйте `.env.example` в `.env` (Mac: `cp .env.example .env`,
   PowerShell: `Copy-Item .env.example .env`). Не перезаписывайте существующий .env:
   перенесите недостающие настройки вручную.
4. Сгенерируйте ключ: `python -c "import secrets; print(secrets.token_urlsafe(32))"`.
   Запишите его в `.env` после `API_KEY=`. Не публикуйте ключ и не коммитьте .env.
5. Терминал API: `python -m uvicorn backend.app.main:app --reload --reload-dir backend`.
6. Второй терминал worker: `python -m backend.worker`.
7. Третий терминал UI (опционально): `python -m streamlit run frontend/app.py`.

На Mac в каждом терминале сначала `source .venv/bin/activate`.
На Windows вместо `python` можно везде использовать `\.venv\Scripts\python.exe`
с точкой перед обратным слешем: `.\.venv\Scripts\python.exe`.

## Проверка через Swagger

Откройте http://127.0.0.1:8000/docs, нажмите Authorize и вставьте API_KEY.
POST /api/v1/analyze → Try it out → выберите .mov → Execute.
Ответ 202 содержит job_id. Подставьте ID в GET /api/v1/jobs/{job_id}.
Повторяйте GET до done / failed. Без worker задание остаётся processing до таймаута.
/health публичный, но отражает только доступность API, не готовность ML/worker.

## Подключение модели для ML-разработчика

Создайте локальную функцию `analyze(video_path: pathlib.Path) -> list[Candidate]`
и укажите `ANALYZER_PATH=ml.inference:analyze` в .env. Перезапустите worker.
Контракт Candidate: backend/app/domain/schemas.py, протокол: ports/analyzer.py.

Для каждого события нужны type, timecode_sec, description, rule, source_title,
source_url, опциональный source_section и evidence_timestamps (1–3 времени).
Pipeline сам читает реальные кадры из видео и кодирует JPEG/base64.
Пустой список означает успешно выполненный анализ без найденных событий;
ошибки модели должны вызывать исключения. Не используйте tests.analyzers
на реальных данных: это исключительно синтетические тестовые функции.
Внешних сетевых запросов в backend нет. Подключаемая модель также должна
работать без облачных API; правовые ссылки должны быть проверены командой.

## Хранение и ограничения первой версии

- База: data/runtime/jobs.sqlite3; файлы: data/runtime/uploads/<uuid>.mov.
- SQLite выбран для локального MVP вместо первоначального PostgreSQL.
- Очередь общая для API и worker, получение задания атомарное.
- Статусы queued/running внутри базы отображаются наружу как processing.
- Таймаут 270 сек от принятия задания (включая очередь), дочерний процесс
  прекращается по таймауту. Это ограничение, а не гарантия качества/скорости модели.
- Просроченные задания переходят в failed, даже после перезапуска worker.
- По умолчанию лимит 100 MiB на файл, 8 незавершённых заданий; переполнение: 429.
- Проверка декодирования выполняется в worker: повреждённый .mov получает failed.
- Один worker, одно видео за раз; модель загружается внутри процесса каждого задания.
  Перед сдачей измерьте скорость на целевом оборудовании и настройте число workers.
- Автоудаление видео пока не реализовано. Перед эксплуатацией добавьте срок хранения
  и очистку, а для публичного URL — HTTPS и лимиты тела запроса в reverse proxy.
- Нормализация времени использует FPS; для видео с переменным FPS потребуется
  извлечение кадров по PTS. Проверяйте таймкоды на предоставленных .mov.
- Публичный URL пока не развёрнут. Это backend-основа, а не готовое решение кейса.

## Тесты

`python -m unittest tests.test_backend -v`

Тесты используют только синтетическое видео и тестовые предикторы.
Проверяют ключ, загрузку/очистку, очередь, сохранение, JPEG, таймаут и отсутствие модели.
